> 仓库归个人还是归组织，决定的是**权限怎么管**：个人仓库靠一个个加协作者，组织仓库靠团队批量授权，项目一旦超过两三个人就该迁到组织下。

## 个人仓库 vs 组织仓库

**个人仓库**挂在你的账号下，`github.com/你的用户名/项目名`。所有权是你一个人的，别人要参与得被你一个个添加为**协作者**（collaborator）。协作者的权限比较粗，基本就是能不能写。

**组织仓库**挂在组织账号下，`github.com/组织名/项目名`。组织是一个容器，里面可以有很多仓库和很多成员。

组织带来的关键能力是**团队（Team）**：把人编成组，然后**按组授权**。新人入职加进「后端组」，他自动获得后端组对所有相关仓库的权限，不用挨个仓库加人。人走了从组里移除，所有权限一次性收回。

几个现实差别：

- **所有权**：个人仓库绑在个人账号上。人离职、账号注销，仓库会很麻烦。组织仓库属于组织
- **权限粒度**：组织仓库支持 Read / Triage / Write / Maintain / Admin 这样的分级角色，个人仓库的协作者机制粗得多
- **计费与策略**：组织可以统一设定安全策略、统一管理套餐

**判断标准很简单：只有你自己写，个人仓库够用；有第二个人长期参与，就该建组织。** 从个人迁到组织 GitHub 提供了转移功能，但迁移会牵动一堆链接和 CI 配置，早做比晚做省事。

## 仓库里那几个标签页

新仓库建好之后，顶上一排标签页很多人只用过前两个。

**Code** —— 代码本体。这里最该花心思的是 **README**，它是仓库的门面，GitHub 会把它渲染在首页。至少写清楚：这是什么、怎么装、怎么用。

**Issues** —— 问题追踪。不只是「报 bug」，也用来记录待办、讨论方案。可以配置 **issue 模板**（`.github/ISSUE_TEMPLATE/`），让提交者按格式填写，省掉大量来回追问。

**Pull requests** —— 见 [[Pull Request]]。

**Actions** —— 见 [[GitHub Actions]]。

**Projects** —— 项目管理看板。

**Wiki** —— 附带的文档空间。

**Security** —— 见 [[GitHub 供应链安全]]。

**Insights** —— 仓库数据统计。

**Settings** —— 仓库设置，分支保护、Pages、密钥都在这里。

下面挑三个容易被忽略的说。

## Projects：轻量项目管理

GitHub Projects 是一块**能和 issue、PR 联动的看板**，官方描述是「可适配的表格、看板与路线图，与 issues 和 pull requests 集成」。

三种视图：

- **Table（表格）** —— 信息密度最高，适合一次看很多条目
- **Board（看板）** —— 经典的待办/进行中/已完成拖动流
- **Roadmap（路线图）** —— 时间线视角，适合排期

**自定义字段**是它比普通看板强的地方。除了内置字段，可以自己加：日期（上线时间）、数字（复杂度估点）、单选（优先级）、文本（备注）、迭代（按周排期）等，**最多 50 个字段**。

最关键的特性是**双向同步**：项目里改了什么（比如重新指派一个 issue），对应的 issue 或 PR 立刻同步更新，反过来也一样。不存在「看板和实际状态对不上」这个经典问题。

对小团队来说，它的好处是**不用再引入一个 Jira**。数据本来就在 GitHub，看板直接长在上面。

## Wiki：用之前想清楚

Wiki 是仓库自带的文档空间，本身也是一个独立的 Git 仓库，可以克隆下来本地编辑。

但它有个现实问题：**Wiki 的内容不跟随分支，也不走 PR 流程**。代码在 `feature` 分支上改了行为，文档在 Wiki 里改了就是立刻生效，两者无法保持版本对应，也无法在同一个 PR 里一起评审。

所以实践中的建议是：**跟代码强相关的文档，放仓库里的 `docs/` 目录**，跟代码一起提交、一起评审、一起打标签。Wiki 留给那些和版本无关的东西——常见问题、会议记录、外部资料索引。

## Insights：仓库的体检报告

Insights 里有一组统计图表，日常真正有用的是这几个：

- **Pulse** —— 最近一段时间的活动摘要，合了多少 PR、开了多少 issue
- **Contributors** —— 谁贡献了多少
- **Traffic** —— 有多少人看了、克隆了你的仓库，开源项目用来判断有没有人在用
- **Dependency graph** —— 依赖关系图，是 [[GitHub 供应链安全]] 里 Dependabot 的数据基础
- **Network / Forks** —— 谁 fork 了你的项目、他们分支的进展

这一块**看看就好，不必当 KPI**。提交数、代码行数这类指标很容易被优化得很难看，用来了解项目大致活跃度足够了。

## 该配的仓库设置

新仓库建好，值得花五分钟配的几项：

- **写 README**，哪怕只有三行
- **加 LICENSE**，见 [[开源协议]]。没有协议的公开仓库，法律上默认是保留全部权利的
- **配 `.gitignore`**，别让依赖目录和构建产物进仓库
- **给主分支加保护**，见 [[Pull Request]] 里的分支保护一节
- **开 Dependabot 和 secret scanning**，见 [[GitHub 供应链安全]]
- **合并方式收敛**：在设置里只保留团队约定的那一种（比如只允许 squash），避免有人手滑选错
- **勾上「合并后自动删除分支」**，省掉手动清理
