> 选哪个撤销命令，只取决于两件事：要撤的东西在哪个区，以及这段历史推给别人了没有——推过了就只能用 `revert` 新增一个提交去抵消，不能改写。

Git 的撤销命令有五六个，名字还长得像，新手最常见的做法是网上搜一条命令直接粘贴，然后把自己的代码搞丢。

其实不用背。先回答下面两个问题，该用哪个命令基本就是唯一的。

## 先问两个问题

**问题一：要撤的东西在哪一层？** 是还没 `add` 的改动，还是已经 `add` 但没提交的，还是已经提交了的？这三层就是 [[Git 三个区]] 讲的三个区，撤销命令是按层分工的。

**问题二：这段历史推到远程了吗？别人可能已经拉走了吗？**

没推过 → 你的地盘，随便改。

推过了 → **只能用「新增一个反向提交」的方式撤销，不能删改已有提交**。原因下面「为什么推过就不能改」一节会讲清楚，这是本篇最重要的一条规矩。

| 我想撤销的 | 用这个 |
| --- | --- |
| 改了文件，还没 `add`，想变回没改的样子 | `git restore <文件>` |
| 已经 `add` 了，想从下次提交里撤出来 | `git restore --staged <文件>` |
| 刚提交完就发现漏了东西 / 信息写错字（没推） | `git commit --amend` |
| 想撤掉最近的一个或几个提交（没推） | `git reset` |
| 想撤掉某个提交，但**已经推了** | `git revert` |
| 刚才手滑，把撤销本身也撤回来 | `git reflog` + `git reset --hard` |
| 想删掉一堆没进过 Git 的临时文件 | `git clean` |

## 看懂 HEAD~1 这种写法

撤销命令里到处是 `HEAD~1`，先说清楚它是什么，不然后面全是天书。

**`HEAD` 是「我现在在哪个提交上」。** 通常就是你当前分支最新的那个提交。

**`~` 是往上数几代。** `HEAD~1` 是 HEAD 的上一个提交，`HEAD~2` 是上上个，`HEAD~3` 再往上一个。`HEAD~1` 也可以写成 `HEAD^`，日常两者等价。

它们只在遇到**合并提交**时才有区别。合并提交有两个父提交，这时候 `^` 用来选第几个父，`~` 则是「顺着第一个父往上数」：

```text
*   860c32b M        <- HEAD，一个合并提交
|\
| * 6a828a5 S
* | 94fa347 B
|/
* fd2e2ed A
```

```text
HEAD^   = B    第一个父提交
HEAD^2  = S    第二个父提交（另一条线）
HEAD~1  = B    等同 HEAD^
HEAD~2  = A    顺着第一个父往上数两代
```

日常撤销用 `HEAD~n` 就够了。`^2` 只在处理合并提交时才碰得到，本篇末尾撤销合并那节会用上。

## restore：丢弃还没提交的改动

```bash
git restore <文件>              # 丢弃工作区改动，恢复成 add 时（或上次提交）的样子
git restore --staged <文件>      # 取消 add，文件内容一个字都不变
git restore --source=HEAD --staged --worktree <文件>   # 两个区一起打回上次提交的样子
```

搞混这两个的人很多，记住区别：**加了 `--staged` 只是「取消 add」，你的改动还在**；不加 `--staged` 是**真的把你写的东西删掉**。

**`git restore <文件>` 是本篇唯一真正救不回来的操作。** 它丢弃的改动从来没进过 Git，后面要讲的 `reflog` 也无能为力——reflog 记的是提交，你没提交过的东西压根不在里面。敲之前把文件名看两遍。

好消息是 `restore` 不动历史、不动分支，所以它跟「推没推过」完全无关，什么时候用都安全。

## commit --amend：修补最近一个提交

场景很具体：提交完一秒钟，发现提交信息打错字了，或者少 `add` 了一个文件。

```bash
git add 忘记的文件
git commit --amend -m "改好的提交信息"
git commit --amend --no-edit          # 只补文件，信息不改，不打开编辑器
```

这里有个新手常误会的点：**它不是「修改」原来那个提交**。提交是只读的，改不了。`--amend` 实际做的是拿暂存区的当前内容**造一个全新的提交，然后把分支指针指过去**，原来那个提交就被晾在一边没人指了。

所以新提交的哈希和原来**不一样**。哈希变了就意味着「历史被改写了」，于是 `--amend` 也受那条规矩管：推过的提交别 amend。

## reset：把分支指针往回搬

`git reset` 是这些命令里最有用、也最容易伤到自己的一个。

它做两件事：**把当前分支的指针挪到你指定的提交**，然后**按模式决定暂存区和工作区要不要跟着变**。

理解它的关键是明白「删提交」是怎么回事。分支就是一个指向某个提交的指针（详见 [[Git 分支与合并]]）。`reset` 并不真的销毁提交，它只是把指针往回挪，那些提交就没有分支指着了，于是从 `git log` 里消失。东西还在，只是找不到入口——这也是为什么后面 `reflog` 能救回来。

三种常用模式的差别，就在于**动几个区**：

| 模式 | 挪分支指针 | 暂存区 | 工作区 | 你的改动 |
| --- | --- | --- | --- | --- |
| `--soft` | 挪 | 不动 | 不动 | 全都还在，且是已 add 状态 |
| `--mixed`（默认） | 挪 | 清 | 不动 | 全都还在，变成未 add 状态 |
| `--hard` | 挪 | 清 | 清 | **没了** |

在一个只有两个提交的仓库上分别执行 `git reset <模式> HEAD~1`，实际结果：

**`--soft`** —— 提交没了，改动原封不动留在暂存区，`git status --short` 显示 `M  f.txt`。

它最经典的用途是**把最近几个零碎提交揉成一个**：

```bash
git reset --soft HEAD~3      # 撤掉最近 3 个提交，改动全留着
git commit -m "合并成一个干净的提交"
```

**`--mixed`**（不写模式时的默认值）—— 提交没了，改动留在工作区但取消了 add，显示 ` M f.txt`。终端会打印：

```text
Unstaged changes after reset:
M	f.txt
```

**`--hard`** —— 提交和改动一起清空，工作区退回目标提交的样子，`git status` 干干净净。终端打印：

```text
HEAD is now at 0f010e9 c1
```

**`--hard` 是这里唯一会毁数据的模式。** 它会连你没提交的改动一起抹掉，而那部分 reflog 救不回来（reflog 只管提交）。已经提交过的内容则一定找得回。

网上大量「怎么撤销 git 提交」的答案上来就给 `git reset --hard`，这是很多人代码丢失的直接原因。**先想清楚工作区里有没有没提交的东西**，有就先 `git stash` 存起来，或者改用 `--soft`。

还有两个不常用但值得知道的模式：

**`--keep`：** 挪指针，但尽量保住你没提交的改动。改动落在跟这次重置无关的文件上时，它照常保留：

```bash
echo WIP > o.txt          # o.txt 跟被撤销的提交没关系
git reset --keep HEAD~1   # 成功，git status 显示  M o.txt，WIP 还在
```

改动正好落在会被重置的文件上时，它**直接中止，而不是覆盖你**——这就是它比 `--hard` 安全的地方：

```text
error: Entry 'f.txt' not uptodate. Cannot merge.
fatal: Could not reset index file to revision 'HEAD~1'.
```

**`--merge`：** 和 `--keep` 类似，区别在于对「已 add 但没提交」的改动处理方式不同。日常用得少，知道有这么个东西就行。

最后一个容易混的地方：`git reset` 还有个**作用在文件上**的形态，`git reset <文件>`，它不挪分支指针，效果等于 `git restore --staged <文件>`。同一个命令名底下两套语义，这正是后来要拆出 `restore` 的原因。

**每次 `reset` 之前，Git 会自动把原来的位置存进 `ORIG_HEAD`。** 刚 reset 完就后悔，最快的路是：

```bash
git reset --hard ORIG_HEAD
```

## revert：用一个新提交去抵消旧提交

`revert` 跟前面几个的思路完全不同：**它什么都不删，而是造一个内容正好相反的新提交，追加在历史末尾**。你改了什么它就改回去，作为一次新的记录。

```bash
git revert HEAD
git revert --no-edit HEAD      # 不打开编辑器写信息，用默认的
```

日志里会多一个提交，原来那个**还好好地在那**：

```text
b9bca1c Revert "引入 bug"
f667901 引入 bug
ac6af80 c1
```

因为只增不改，`revert` 是**唯一能安全用在已经推送的提交上的撤销方式**。团队协作里默认选它。

两个细节：

**撤销合并提交必须加 `-m`。** 合并提交有两个父提交，Git 不知道你想回到哪条线上去，得用 `-m <父提交编号>` 告诉它，编号从 1 开始，`-m 1` 一般指主线：

```bash
git revert -m 1 <合并提交的哈希>
```

**`revert` 也可能冲突。** 你要撤的是很久以前的提交、而后来的代码又动过同一块地方时，Git 没法自动决定，会停下来让你手工处理。流程跟 [[Git 分支与合并]] 里的冲突解决完全一样，最后用 `git revert --continue` 或 `--abort` 收尾。

## 为什么推过就不能改

这条规矩前面提了好几次，讲清楚原理你就不会想去违反它。

假设你和同事都有 `main` 分支，最新提交是 `abc123`。同事已经 `pull` 过，他电脑上也有 `abc123`。

现在你用 `reset` 撤掉它，重新提交，得到一个新提交 `def456`——内容也许一模一样，但**哈希不同，在 Git 眼里就是完全不同的提交**。你强行推上去，远程的 `abc123` 就没了。

同事那边的麻烦就来了：他本地还留着 `abc123`，还可能在它上面接着写了新代码。他下次 `pull`，Git 看到两边历史对不上，只能给他一堆冲突，或者把 `abc123` 的内容重新塞回去——你辛苦撤掉的东西又回来了。人越多越乱。

所以规矩是：**公共分支上只用 `revert`。** `reset`、`--amend`、后面 [[Git 分支与合并]] 会讲的 `rebase`，这些会改写历史的操作，只在自己还没推的分支上用。

真的非改共享历史不可时，用 `--force-with-lease` 而不是 `-f`：

```bash
git push --force-with-lease
```

区别在于，`--force-with-lease` 会先检查远程是不是还停在你以为的位置，别人在你之后推过东西它就拒绝执行；`-f` 是无条件覆盖，直接把别人的提交冲掉。

## reflog：撤销操作的后悔药

前面说 `reset --hard` 之后提交「还在，只是没有分支指着」。`git reflog` 就是找回它们的入口。

它记录 **HEAD 每一次移动**，包括那些已经不在任何分支上、`git log` 完全看不见的提交：

```bash
git reflog
```

```text
ac6af80 HEAD@{0}: reset: moving to HEAD~2
b9bca1c HEAD@{1}: revert: Revert "引入 bug"
f667901 HEAD@{2}: commit: 引入 bug
ac6af80 HEAD@{3}: commit (initial): c1
```

从上往下是从新到旧。找到 reset 之前那一行的哈希，回去就行：

```bash
git reset --hard b9bca1c
```

误删分支、reset 到错的地方、rebase 搞砸了，都从这里救。**动手撤销之前先跑一次 `git reflog` 记下当前哈希**，是个能省很多事的习惯。

两个边界得知道：reflog 是**纯本地的**，每个仓库自己一份，你克隆到另一台电脑上没有这边的 reflog，别人也看不到你的；它**有过期时间**，被 `git gc` 清理之后就真找不回了，所以它是后悔药，不是备份方案。

## 常见坑

**`git checkout` 的双重身份。** `git checkout <分支>` 是切分支，`git checkout -- <文件>` 是丢弃改动，少打两个横杠意思天差地别，而且后者会真的删掉你的改动。用 `git switch` 和 `git restore` 就绕开了这个雷。

**未跟踪的文件不受任何撤销命令影响。** `reset --hard` 不会删它们，因为 Git 压根不认识它们。要清理得用 `git clean`，而且**一定先用 `-n` 预演**：

```bash
git clean -n -d      # 只打印会删哪些，不动手
git clean -f -d      # 看清楚了，确认删
```

`-n` 是预演，`-f` 是真删，`-d` 表示连目录一起。`git clean` 删的是从没进过 Git 的文件，删完任何地方都找不回，那步预演别省。

**撤销之前先看一眼 `git status`。** 三个区里各有什么、有没有没提交的东西，看一眼就清楚了，比事后翻 reflog 省事。
