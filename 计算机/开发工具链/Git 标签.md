> 标签是给某个提交起的一个固定名字，用来标记「这里是 v1.2.0」；日常一律用附注标签（`-a`），因为它是个真正的对象，能记下是谁、什么时候、为什么打的。

## 标签解决什么问题

提交的哈希是 `d72c8c9` 这种没法记的东西。发布 1.0 版本三个月后，你想知道「当时上线的到底是哪个提交」，翻 `git log` 一个个找会很痛苦。

标签就是给那个提交贴一个人能读的名字。贴完之后 `v1.0.0` 和那串哈希等价，任何接受提交的命令都能用它：

```bash
git show v1.0.0
git diff v1.0.0 v1.1.0
git switch --detach v1.0.0
```

**标签和分支的区别是：分支会动，标签不动。** 分支指针每次提交都往前挪一格（见 [[Git 分支与合并]]），标签打上去就钉死在那个提交上。这正是发布标记需要的语义。

## 两种标签，用附注的那种

Git 有两种标签，区别不是「加不加说明」，而是**底层是不是一个独立对象**。

**轻量标签（lightweight）** 就是一个存着提交哈希的文件，跟分支一样，只是不会移动：

```bash
git tag v1.0-light
```

**附注标签（annotated）** 会在版本库里造一个**真正的标签对象**，里面存着打标签的人、时间和说明：

```bash
git tag -a v1.0 -m "第一个正式版本"
```

差别可以直接看出来。用 `git cat-file -t` 查对象类型：

```bash
git cat-file -t v1.0-light    # 输出 commit —— 它直接就指向提交
git cat-file -t v1.0          # 输出 tag    —— 它是个独立的标签对象
```

附注标签里面存了什么：

```bash
git cat-file -p v1.0
```

```text
object 89792571ff620378e8d35eaaf5a6d50b47749977
type commit
tag v1.0
tagger T <t@t.t> 1787902256 -0700

第一个正式版本
```

轻量标签没有这些，`git show` 一个轻量标签只会显示那个提交本身，看不出标签是谁什么时候打的。

**结论很简单：发布用的标签一律 `-a`。** 轻量标签留给「临时做个记号，一会儿就删」的场景。

`git tag -n` 可以列出标签带说明，一眼看出两者差别：

```bash
git tag -n
```

```text
v1.0            第一个正式版本
v1.0-light      第一版
```

轻量标签那行显示的是**提交信息**，因为它自己没有说明可显示。

## 日常命令

```bash
git tag                          # 列出所有标签
git tag -n                       # 带说明列出
git tag -l "v1.*"                # 按模式筛选
git tag -a v1.0.0 -m "说明"       # 给当前提交打附注标签
git tag -a v1.0.0 <提交哈希> -m "说明"   # 给历史上某个提交补打
git show v1.0.0                  # 看标签和它指向的提交
git tag -d v1.0.0                # 删除本地标签
```

删除时的输出会告诉你删掉的是哪个提交上的标签：

```text
Deleted tag 'v1.0-light' (was 8979257)
```

## 最大的坑：标签不会自动推送

这条单独拎出来，因为几乎每个人都踩过。

**`git push` 不推标签。** 你在本地打好了 `v1.0.0`，推完代码去 GitHub 上看 Releases，空的。

要显式推：

```bash
git push origin v1.0.0        # 推一个标签
git push origin --tags        # 推所有本地标签
git push --follow-tags        # 推分支，同时带上「相关的」附注标签
```

`--follow-tags` 是最常用的一个，它只推那些指向即将被推送的提交的**附注标签**，不会把你本地那些临时轻量标签一股脑传上去。

删远程标签的写法不太直观：

```bash
git push origin --delete v1.0.0
```

**已经推出去的标签不要改。** 别人拉过之后，你在本地把标签移到别的提交再强推，他们本地的旧标签不会自动更新，于是同一个 `v1.0.0` 在不同人机器上指向不同提交——这种问题排查起来非常费劲。发错了就打一个新版本号，别动老的。

## 检出标签会进入分离头指针

```bash
git switch --detach v1.0.0
```

```text
HEAD is now at 8979257 第一版
```

此时 `.git/HEAD` 里直接是哈希，不是 `ref:`，你处在分离头指针状态（详见 [[Git 分支与合并]]）。**在这里改代码提交，切走之后就找不到了。**

要基于某个版本做修复，先建分支：

```bash
git switch -c hotfix-1.0.1 v1.0.0
```

## 配合语义化版本

标签名怎么起，事实标准是语义化版本（SemVer），格式 `主版本.次版本.修订号`：

- **主版本**：不兼容的改动。用户升级要改代码
- **次版本**：新增功能，向后兼容。用户升级不用改代码
- **修订号**：修 bug，向后兼容

```text
v1.4.2
 │ │ └── 修了个 bug
 │ └──── 加了新功能，老代码照常跑
 └────── 有破坏性改动，老代码可能跑不了
```

加不加 `v` 前缀都有人用，GitHub 上 `v1.4.2` 更常见一些。同一个项目里保持一致就行。

标签在 GitHub 上还有个额外作用：**推送标签可以触发 workflow**，也是 Releases 页面的基础。发版流水线通常就是「打标签 → 推标签 → Actions 自动构建产物并创建 Release」，见 [[GitHub Actions]]。
