> Git LFS 把大文件挪到另一个服务器上存，仓库里只留一个几百字节的**指针文件**，让 Git 不必为每一版设计稿、模型、视频都存一份完整拷贝。

## 为什么普通 Git 扛不住大文件

Git 存的是**快照**，不是差异。你改一个 200 MB 的视频文件，哪怕只改了一帧，Git 也会为新版本再存一份完整的对象。

后果是雪球式的：这个文件改十次，仓库里就躺着十份 200 MB，两个 G。而且 **Git 的历史是不可变的**，你没法「删掉旧版本腾地方」——旧对象还在历史里，谁克隆仓库都得把整整两个 G 全拉下来，包括那些他永远用不到的老版本。

对文本代码这不是问题，因为 Git 压缩后差异很小。对二进制文件（设计稿、音视频、模型权重、编译产物）就是灾难：它们压缩不动，每一版都是实打实的体积。

GitHub 还有**单文件大小上限**，超了直接推不上去。按套餐不同：GitHub Free 和 Pro 是每个文件 2 GB，Team 4 GB，Enterprise Cloud 5 GB。超过 5 GB 的文件会被 Git LFS 拒绝并报错。

## 它怎么解决

思路很直接：**大文件本体不进 Git 仓库，只在仓库里留一张「提货单」。**

这张提货单就是**指针文件**，纯文本，几百字节，长这样：

```text
version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b1258daaa5e2ca24d17e2393
size 12345
```

三行分别是：LFS 规范版本、文件内容的 sha256 指纹（`oid`，object id）、原文件字节数。

Git 仓库里存的、参与版本控制的、被别人克隆下来的，就是这三行文本。真正的大文件存在另一台 LFS 服务器上（用 GitHub 就是 GitHub 的 LFS 存储）。

你 `git checkout` 到某个版本时，LFS 客户端看到指针文件，拿着 `oid` 去服务器把对应的真实文件下载下来，替换到工作区。**你在编辑器里看到的一直是真实文件，中间这套调包是透明的。**

好处是历史里每一版只占几百字节。克隆仓库时默认只拉当前版本需要的大文件，不会把十个历史版本全拖下来。

## 怎么用

**第一步，装 Git LFS。** 它不是 Git 自带的，是个独立程序（`git-lfs`），得单独安装。装完在仓库里初始化一次：

```bash
git lfs install
```

**第二步，告诉它哪些文件要走 LFS。** 按文件类型匹配：

```bash
git lfs track "*.psd"
```

**第三步，也是最容易漏的一步：把 `.gitattributes` 提交上去。**

`git lfs track` 做的事情是往仓库根目录的 `.gitattributes` 文件里写一条规则。这个文件**必须提交进仓库**：

```bash
git add .gitattributes
git commit -m "配置 LFS 跟踪 psd 文件"
```

官方明确建议提交它，理由有三个：写在全局配置里会和其他项目打架；提交进仓库后协作者和 fork 你项目的人自动获得同样的规则；归档仓库时 LFS 对象才能被正确包含。

**忘了提交 `.gitattributes` 的后果**：只有你这台机器知道要走 LFS，同事推上来的 psd 会以完整二进制进普通 Git 仓库，前面说的问题原样发生。

之后正常 `git add`、`git commit`、`git push` 就行，LFS 会自己接管匹配到的文件。

## 最大的坑：只对之后的提交生效

**`git lfs track` 不会追溯处理已经提交过的文件。**

你的 psd 已经提交过十次了，现在配上 LFS，那十个历史版本仍然完整地躺在 Git 历史里，仓库该多大还是多大。LFS 只管从现在开始的新提交。

官方给的处理办法是：**先把这些文件从仓库里移除，再作为 LFS 文件重新加进来。** 真要把历史里的大文件彻底清干净，需要重写整个仓库历史（`git filter-repo` 之类的工具），那会改变所有提交的哈希——也就是 [[Git 撤销操作]] 里说的「改写已推送历史」，团队里所有人都得重新克隆。

**所以 LFS 最好在项目一开始就配好。** 等仓库已经被大文件撑到几个 G 再补救，代价大得多。

## 用之前想清楚的事

**LFS 有配额，而且要花钱。** 大文件存在 GitHub 的 LFS 存储上，存储空间和下载流量都是单独计费的。团队一多、CI 频繁拉取，流量消耗会比想象中快。

**它给协作增加了一个前提**：每个协作者、每台 CI 机器都得装 Git LFS。没装的人克隆下来，工作区里的 psd 就是那三行文本而不是图片——这个现象第一次遇到会很困惑。

**并不是所有大文件都该进 LFS。** 编译产物、依赖包、日志这些根本不该进版本控制，写进 `.gitignore` 就行。LFS 是给那些**确实需要版本管理的**大文件用的：设计稿、游戏素材、测试用的样本数据、模型权重。
