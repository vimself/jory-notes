> 给开源项目贡献代码的标准路径是 fork → 开分支 → 改 → 提 PR；技术动作十分钟就能学会，真正决定 PR 会不会被合的是**改之前有没有先沟通**。

## 为什么要 fork

你对别人的仓库没有写权限，推不上去。所以流程是：

1. 把对方仓库 **fork** 一份到自己账号下（这是一份你有完全权限的副本）
2. 在自己那份里改
3. 向原仓库提 [[Pull Request]]，请他们把你的改动拉过去

这里出现两个仓库，术语上区分为：

- **upstream（上游）** —— 原项目仓库，你只能读
- **origin** —— 你 fork 出来的那份，你能读能写

搞清楚这两个名字，后面的命令就不会乱。

## 走一遍完整流程

**第 0 步：先沟通，别急着写代码。**

这一步最容易被跳过，也最容易导致白干。正确做法是先开一个 issue，或者在已有 issue 下留言，说明你想改什么、打算怎么改，等维护者回应。

原因很实际：你觉得是 bug 的可能是设计如此；你想加的功能可能已经被讨论过并否决了；你选的实现方式可能和项目的规划冲突。**写完三百行才被告知方向不对，是开源新手最常见的挫败来源。**

很多项目会用 `good first issue` 或 `help wanted` 标签标出适合新人的任务，从这些入手最稳妥。

**第 1 步：读 CONTRIBUTING。**

大部分成熟项目的根目录或 `.github/` 下有 `CONTRIBUTING.md`，写着这个项目的规矩：代码风格、提交信息格式、测试要求、PR 该提到哪个分支。**读它比问人快。**

**第 2 步：fork 并克隆。**

网页上点 Fork，然后：

```bash
gh repo fork owner/repo --clone
```

或者手动：

```bash
git clone git@github.com:你的用户名/repo.git
cd repo
git remote add upstream git@github.com:owner/repo.git
```

第二条命令是关键：**把原仓库添加为 `upstream` 远程**，这样才能持续同步他们的更新。

确认一下：

```bash
git remote -v
```

应该能看到 `origin`（你的）和 `upstream`（人家的）两组。

**第 3 步：开分支。**

```bash
git switch -c fix/修正登录超时
```

**别在 `main` 上改。** 你的 `main` 应该始终是上游的镜像，用来同步；改动全部走分支。一个 PR 一条分支。

**第 4 步：改代码。**

跟着项目的规矩来：跑它的测试、按它的风格写、提交信息按它的格式。如果项目用 [[Git 分支与合并]] 里说的约定式提交或者别的规范，照做。

**第 5 步：推到你的 fork。**

```bash
git push -u origin fix/修正登录超时
```

**第 6 步：提 PR。**

```bash
gh pr create --repo owner/repo --base main
```

注意 `--repo` 指向的是**上游**。描述里说清楚：解决什么问题、怎么解决的、怎么验证。如果对应某个 issue，写上 `Fixes #123`，合并时会自动关闭那个 issue。

**第 7 步：响应评审。**

维护者提了意见就改，改完推到同一条分支，PR 自动更新。来回几轮是常态，轮数一般取决于改动大小和维护者对这块代码的熟悉程度。

有些项目会要求你在合并前把提交整理一下（squash 成一个、或者 rebase 到最新的上游），照做即可，方法见 [[Git 分支与合并]]。

## 保持 fork 与上游同步

你的 fork 不会自动跟进上游的更新。分支开久了，上游已经往前跑了几十个提交，你的改动很可能冲突。

同步方法：

```bash
git switch main
git fetch upstream
git merge upstream/main      # 或 git rebase upstream/main
git push origin main
```

用 `gh` 一条命令也行：

```bash
gh repo sync
```

**动手改之前先同步一次**，能省掉大量后续冲突。分支开了很久的话，中途也同步一下，把冲突分散着解决，比最后一次性解一大堆容易。

## 会遇到的两个法律文件

**DCO（Developer Certificate of Origin）** —— 有些项目要求每个提交都带一行签名，声明这段代码是你有权提交的：

```bash
git commit -s -m "修正登录超时"
```

`-s` 会自动追加一行 `Signed-off-by: 你的名字 <邮箱>`。忘了加的话 CI 会直接把 PR 卡住，补救办法是 `git commit --amend -s` 或者对多个提交做 rebase 重新签名。

**CLA（Contributor License Agreement）** —— 部分由公司主导的项目要求你签一份贡献者协议，通常是首次提 PR 时机器人自动引导你在网页上签。它涉及你对贡献代码的授权范围，**大额或涉及职务作品时值得先看清条款**。

两者的关系见 [[开源协议]]。

## 让 PR 更容易被合的几条

**改动要小。** 一个 PR 只做一件事。修 bug 就只修 bug，别顺手重构、别顺手改格式——格式改动会把真正的改动淹没在 diff 里。

**别提纯格式化的 PR。** 未经沟通就把整个项目重新格式化一遍，是最容易被直接关闭的一类 PR。

**补上测试。** 修了 bug 就加一个能复现该 bug 的测试用例，这会显著提升可信度。

**耐心。** 维护者大多是业余时间在做，几天甚至几周没回复是常态。可以礼貌地跟进一次，别催。

**被拒时先看理由。** 维护者通常会说明为什么不合：是方向不符，还是实现方式要改。前者意味着这个功能本就不该进上游，代码留在自己的 fork 里照常用；后者按意见改完可以再提。
