> Pull Request 是一个「我这条分支想合进你那条分支，先看一眼」的请求；它本身不是 Git 的功能，而是 GitHub 在 Git 的分支和合并之上加的一层协作流程。

## 名字为什么这么怪

「Pull Request」直译是「拉取请求」，方向听着是反的：你想把代码推进对方的仓库，名字却在说拉取。

这个名字来自开源协作的场景。你没有对方仓库的写权限，推不进去，能做的是把代码放在自己的仓库里，然后**请求对方来拉**——「请你把我的改动拉过去」。

GitLab 把同样的东西叫 Merge Request（MR），那个名字其实更贴近现在的用法。

## 它在 Git 之上加了什么

先分清楚：**合并这件事 Git 自己就能做**（见 [[Git 分支与合并]]）。你完全可以本地 `git merge feature` 然后推上去，不需要任何 PR。

PR 加的是**合并之前的那一段流程**：

- **一个可讨论的场所**：改动以 diff 的形式摊开，别人可以逐行评论
- **一道自动检查的关卡**：CI 跑测试、跑 lint，不过不让合（见 [[GitHub Actions]]）
- **一条审批记录**：谁批准的、什么时候、基于哪一版代码，永久留档
- **一个可执行的强制点**：配合分支保护，可以做到「没人批准就物理上合不进去」

一句话：**PR 把「合并」从一个技术动作，变成一个有门禁的流程。**

## 两种协作模式

**分支模式（Shared Repository）**：你有仓库写权限。直接在同一个仓库里开分支、推上去、提 PR。团队内部项目基本都这样。

```bash
git switch -c feature/登录页
# 改代码、提交
git push -u origin feature/登录页
```

**Fork 模式**：你没有写权限，常见于给开源项目贡献代码。你先把对方仓库 fork 一份到自己账号下，在自己那份里改，然后向原仓库提 PR。完整流程见 [[开源贡献流程]]。

两种模式提出来的 PR，在 GitHub 界面上长得一模一样，区别只在源分支属于谁。

## 走一遍完整流程

**1. 开分支改代码。** 别在 `main` 上直接改——`main` 通常有保护，而且 PR 的本质就是「拿一条分支去比另一条分支」，没有分支就没有 PR。

**2. 推上去。** 推完之后 GitHub 网页上通常会直接冒出一个「Compare & pull request」的按钮。

**3. 创建 PR。** 要选两个东西：**base**（要合进哪里，通常是 `main`）和 **compare**（你的分支）。方向别搞反。

用 `gh` 命令行也行，它已经内置了这套流程：

```bash
gh pr create --base main --title "新增登录页" --body "说明..."
```

**4. 写清楚描述。** 这是最容易糊弄、但回报最高的一步。审查者看的第一眼是描述，不是代码。至少写：改了什么、为什么改、怎么验证。项目如果配了 PR 模板，按模板填。

**5. 等 CI 和评审。** 这期间你还能继续往同一条分支推提交，**PR 会自动更新**，不需要重新创建。这一点新手常误会。

**6. 处理评论。** 评审者可以在具体某一行上留评论。你改完推上去，那条评论线程会标记为已解决。

**7. 合并。** 三种合并方式，下一节细说。

**8. 删分支。** 合完 GitHub 会问你要不要删源分支。**删。** 尤其是用了 squash 合并的（原因见 [[Git 分支与合并]]），留着继续用会制造大量冲突。

## 三种合并方式怎么选

GitHub 的合并按钮有三个选项，对应的历史结果完全不同。

**Merge commit（合并提交）** —— 保留 PR 分支上的每一个提交，并额外加一个明确的合并点。相当于 `--no-ff` 的 merge。适合希望完整保留协作过程的团队。

**Squash and merge（压缩合并）** —— 把 PR 里的所有提交**压成一个**放到目标分支上。你那 20 个「改错别字」「再改一下」的零碎提交，在 `main` 上只留一行。

主干历史非常干净，代价是中间过程在 `main` 上丢失了。官方也明确提醒：**它不适合长期存在的分支**——后续的 PR 可能包含已经被压进主干的提交，冲突概率显著上升。

**Rebase and merge（变基合并）** —— 把每个提交**逐个**接到目标分支上，不产生合并提交，历史是直线且保留了每个提交。

这个选项有两条 GitHub 特有的行为，和你本地 `git rebase` 不一样：

- 它**总是更新 committer 信息并生成新的提交哈希**
- 它会**丢弃那些本来就是空的提交**

日常怎么选：**内部项目用 squash 最省事**，主干一个特性一行，谁改的什么一目了然。需要保留完整开发脉络的用 merge commit。rebase and merge 用得最少，因为它既改哈希又不留合并点，出问题时不好追溯。

## 分支保护：让规则真正生效

光靠口头约定「不许直接推 main」是拦不住手滑的。分支保护是把它变成硬性限制。

在仓库设置里给 `main` 加保护之后，可以要求：

- **合并前必须有 PR 评审**，并指定需要几个人批准
- **必须通过指定的状态检查**（CI 跑绿了才让合）
- **所有评论必须解决完**
- **提交必须有签名**
- **保持线性历史**（禁止合并提交，只能 squash 或 rebase）
- **使用合并队列**，自动确保合入时基于的是最新代码
- **必须成功部署到指定环境**之后才能合
- **锁定分支**（只读）
- **限制谁能推送**、能不能强推、能不能删除分支
- **是否对管理员同样生效**

最后一条容易被忽略：默认情况下管理员可以绕过这些规则。真想让规则可靠，得勾上对管理员也生效。

**Rulesets（规则集）是分支保护的新形态。** 两者能做的事高度重合，关键差别在叠加方式：**分支保护规则同一时间只有一条能生效**，多条规则匹配同一个分支时会产生歧义；规则集没有这个限制，可以叠加。新项目直接用规则集，老仓库 GitHub 提供了转换功能。

## 用 gh 命令行操作 PR

装了 `gh` 之后（见 [[GitHub 自动化接口]]），整个流程不用离开终端：

```bash
gh pr create          # 创建
gh pr list            # 列出仓库里的 PR
gh pr status          # 看跟我有关的 PR
gh pr view            # 查看当前分支对应的 PR
gh pr diff            # 看改动
gh pr checks          # 看 CI 状态
gh pr review          # 提交评审意见
gh pr merge           # 合并
gh pr checkout <编号>  # 把别人的 PR 拉到本地检出，方便实际跑一跑
```

`gh pr checkout` 尤其实用：审查别人的代码时，光看 diff 经常看不出问题，把它拉到本地实际跑一遍要可靠得多。

## 一些实践

**PR 要小。** 一个 PR 只做一件事。改了 3000 行的 PR 没人能认真审，最后就是走过场点个同意。真要做大改动，拆成一串小 PR 依次合入。

**先自己审一遍。** 提交之前自己把 diff 从头看一遍，能发现大量遗留的调试代码和手滑改动。

**Draft PR 用来提前要反馈。** 代码没写完就想确认方向对不对，开成草稿状态提出来，标题写清楚在问什么。

**评审是对代码不是对人。** 提意见针对具体那行代码和具体的问题，别泛泛评价。
