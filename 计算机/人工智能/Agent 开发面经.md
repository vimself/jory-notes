> Agent 开发岗的面试题几乎都绕着同一条主线转：模型只是零件，决定产品好坏的是你套在模型外面那层东西——工具、上下文、循环、验证。把每道题挂回这条主线，比背定义管用。

你投了一个 AI Agent 开发岗，简历上写着「熟练使用 Claude Code」。面试官不会考你注意力机制的公式，他会问：你平时怎么用？为什么这么用？出问题了怎么定位？这几道题看着散，其实在验一件事：你有没有真把 Agent 当工程系统来搭。下面按我实际被问到的顺序记录，每题先给能直接说出口的答案，再补上被追问时用得上的东西。

## 面试官在考的三层

答题前先建立坐标系，不然容易答得又碎又浅。这类岗位的问题基本落在三层上，从浅到深：

1. **会不会用**——用过哪些工具，工作流长什么样。考的是熟练度，好糊弄
2. **懂不懂机制**——skill 是什么、agent 是什么。考的是你知不知道底下在发生什么
3. **会不会设计**——harness、loop、goal。考的是你能不能自己搭一套

第三层是分水岭。前两层背一背也能过，第三层答不出来，面试官立刻知道你只是个重度用户。

## 用过哪些 AI coding 工具

我用得最多的是 Claude Code，另外接触过 OpenAI 的 Codex。Claude Code 本身有多种形态：终端 CLI、桌面应用、网页版（claude.ai/code），以及 VS Code 和 JetBrains 的 IDE 插件，底下是同一套东西。

这题的坑在于**只报菜名**。面试官问「差异是什么」，想听的是你有没有对比的维度。我会按这几条展开：

- **形态**：CLI、IDE 插件、还是云端跑。CLI 的好处是能被脚本调用，能塞进 CI；IDE 插件的好处是选中代码就有上下文
- **上下文怎么拿**：靠你手动贴，还是它自己会去 grep、读文件、翻 git 历史。这条直接决定了能不能处理大仓库
- **扩展性**：有没有 hooks（在工具调用前后插入你自己的脚本）、skills、MCP（Model Context Protocol，让 Agent 接外部数据源和工具的协议）。没有扩展点的工具，只能用它设想过的用法
- **权限模型**：能不能细粒度控制「哪些命令免确认、哪些必须问我」。要做无人值守，这条是前提
- **能不能长时间跑**：会话被压缩后还记不记得任务，能不能跨会话续上

按维度答，哪怕你只深用过一个工具，也显得你想过这件事。

## 你的 AI coding 工作流是怎样的

拿到一个开放性需求，我的流程是六步。**核心排序原则只有一句：越靠前的阶段返工越便宜。** Agent 开发里最贵的失败从来不是代码写错，是方向错了还一路写下去。

**第一步，把需求磨清楚。** 我会用 skill 驱动多轮追问，反复对撞到方向明确为止。这一步坚决不让它写代码——一旦开始产出代码，沉没成本会让你不愿意推翻方向。

**第二步，按软件工程原理拆阶段。** 把方向拆成模块，模块拆成能独立验收的阶段。判据是「这个阶段做完，我能不能单独验证它对不对」，不能就继续拆。

**第三步，前端先定型再生成代码。** 涉及界面的部分，我先用 Claude Design 的画布把界面定下来，再把分享 URL 交给 Claude Code 去生成实现。让 Agent 直接从文字描述写界面，出来的东西你得改十轮；先把视觉定死，它只需要翻译。

**第四步，分阶段实现，留工作痕迹。** 每个阶段单独跑，进度、决策、待办都写进文件。

「留痕迹」这条不是洁癖，是刚需。会话上下文长到一定程度会被压缩，压缩时丢什么不由你控制；换个会话更是从零开始。**写进文件的东西才是跨会话唯一可靠的记忆**，聊天记录里的不算。这一条我吃过亏才明白。

**第五步，code review 加功能 review。** 整个流程最耗时的就是这里，反复 debug 到能上线为止。心理上要接受：生成阶段快得不真实，省下的时间会在 review 阶段还回来一部分。

**第六步，部署。** 让跑在云端服务器上的 Claude Code 执行上线。

被追问「为什么不直接让它一把梭」时，答案是：一把梭的失败模式是它在第 800 行的时候基于第 20 行的一个错误假设继续往下写，而你要到全部跑完才发现。分阶段的本质是**把验证点前移**。

## 怎么理解 Skill

一句话：**技能说明手册**，让 Agent 快速进入你预设好的工作流。

往下一层，Skill 是磁盘上的一个目录，核心是 `SKILL.md`：

```text
.claude/skills/my-skill/
├── SKILL.md          # 必需：概览与导航
├── reference.md      # 详细资料，用到时才读
└── scripts/
    └── helper.py     # 脚本，是被执行的，不是被读进上下文的
```

`SKILL.md` 开头是 YAML frontmatter：

```yaml
---
name: my-skill
description: What this skill does
allowed-tools: Read Grep
disable-model-invocation: true
---

技能正文写在这里。
```

**它怎么加载才是重点**，官方叫渐进式披露（progressive disclosure）。启动时，Agent 只拿到所有技能的 `description`；只有当某个 description 和你的请求对上了，正文才会被读进来。

这条机制推出两个结论，都是面试可以直接说的：

- **`description` 是整个技能里最重要的字段。** 它是唯一常驻上下文的部分，决定技能会不会被触发。正文写得再好，description 没写对，它永远不会被想起来
- **技能可以写得很长而几乎不花成本。** 用不到就不加载。这和 `CLAUDE.md` 正好相反——`CLAUDE.md` 每个会话都全量加载，所以要精简；技能按需加载，所以能详尽

这个知识库自己就有一个：`.claude/skills/humanizer-zh/`，写笔记时用来去 AI 腔。

## 怎么理解 Agent

一句话：**你的一个小员工**，或者叫子代理（subagent）。给它需求，让它自己干到出成果。

但面试时只说到这儿会被追问「那和我自己多开一个会话有什么区别」。区别是**上下文隔离**，这才是重点。

子代理跑在自己独立的上下文窗口里。它读了 50 个文件翻遍整个仓库，这些内容**不消耗主会话的上下文**；回到主会话的只有它最后那段文本回答，外加 token 数和耗时。

为什么这件事重要：主会话的上下文是稀缺资源，而探索型任务偏偏最耗上下文——翻半天仓库只为确认一个函数在哪。用子代理，等于**拿一个可丢弃的上下文去换一句结论**。

配置也是一个 Markdown 文件，放在 `.claude/agents/` 下：

```markdown
---
name: code-improver
description: Scans files and suggests improvements. Use after writing or modifying code.
tools: Read, Grep, Glob
model: sonnet
---

You are a code improvement specialist...
```

`tools` 是白名单：**写了就只有这些，没列的一律没有**，包括 MCP 工具。上面这个只读工具集意味着它物理上改不了文件，比在 prompt 里写「请不要修改文件」可靠得多。**能力约束优于口头约束。**

两个容易踩的坑：

- **子代理是冷启动的。** 它没有你会话里的任何上下文，所以派活的 prompt 必须自包含。你觉得「它应该知道」的事，它都不知道
- **它不会替你保留过程。** 主会话只拿得到最终回答，中间读了什么、试过什么都没了。要留证据就让它写文件

这个知识库里也有一个：`.claude/agents/humanizer-check.md`，只给了 `Read, Grep, Glob`，所以它只能报告问题，改不了笔记。

## 怎么理解 Harness 工程

先纠正我自己一开始的误听：这个词是 **harness**，不是 hermes。而它的字面意思就是**挽具、马具**，所以「给大模型装马鞍」这个比喻其实是直译。

官方术语表的定义是：agentic harness 指把语言模型变成主动编码 Agent 的那套**工具、上下文管理和执行环境**。在 Claude Code 这个例子里，模型是 Claude，harness 是 Claude Code——它提供文件访问、shell 执行、权限门控和记忆加载。

为什么需要马鞍：模型本身的能力强，但是**发散的**。同一匹马，没有鞍具你只能让它自己跑；装上鞍辔，你才能决定它往哪跑、跑多快、什么时候停。

harness 具体包含什么，答这几样就够：

| 组成 | 干什么 | 缺了会怎样 |
| --- | --- | --- |
| 工具 | 读写文件、执行命令、联网 | 模型只能空谈，碰不到真实世界 |
| 上下文管理 | 决定什么进上下文、什么时候压缩 | 长任务跑着跑着就失忆 |
| 执行环境 | 沙箱、工作目录、依赖 | 没法验证，只能靠猜 |
| 权限门控 | 哪些操作要人确认 | 不敢让它无人值守 |
| 记忆加载 | `CLAUDE.md`、skills、历史 | 每次都要从头交代一遍 |

**harness 和幻觉的关系是这题最能加分的地方。** 直觉上大家会去 prompt 里写「不要编造」，但那基本没用。真正压幻觉的是**让模型能自己验证**：能跑测试，就知道代码到底过没过；能读到真实报错，就不用猜错在哪；能 grep 仓库，就不用凭印象说某个函数存在。

所以那句「避免幻觉」要展开成：**harness 不是靠约束模型来减少幻觉，是靠给模型接上现实的反馈回路。** 这也是为什么同一个模型，配不同的 harness，效果能差出一个量级。

这就是它被叫做「系统性工程」的原因——真正要设计的是工具边界、上下文策略、权限模型、失败恢复，模型本身反而是里面最不需要你操心的部分。

## 怎么理解 Goal 与 Loop 工程

这两个概念是一回事的两面，统称 Loop 工程。核心思路：让 Agent 在「行动 → 观察结果 → 推理 → 再行动」的循环里自己跑，不用每一步都等你敲回车。

常见的循环有四类：

- **心跳循环（heartbeat）**：固定间隔一直跑
- **定时循环（cron）**：按时间表跑，比如每天早十点
- **钩子循环（hook）**：被事件触发，比如 PR 推送、CI 失败
- **目标循环（goal）**：**迭代到成功条件满足才停**

goal 循环就是我理解的「goal 工程」，它和前三类的区别在于**有退出条件**。前三类是「一直跑」，goal 是「跑到成不成为止」。

它适合的场景，我的判断是三条同时成立：**目标非常明确且标准化、不在乎过程怎么实现、单次实现耗时长**。这三条凑齐时，你守在旁边一步步确认纯属浪费。

**成败全看退出条件能不能被机器验证。** 这是这题唯一必须答对的点：

- 「让所有单元测试通过」是好目标：机器跑一下就知道成没成
- 「让这段代码更优雅」是坏目标：判定不了，循环要么永远不停，要么在某个随机的地方停下来说自己做完了

把「不在乎过程」和「不在乎结果」分清楚也重要。goal 循环放弃的是对**过程**的控制，对**结果**的判定反而要求更高——正因为你不看着，判据必须硬到能自动执行。

长时间无人值守跑起来，还得配齐这几样：**计划、验证手段、权限边界、日志、检查点，以及人能插进去的位置**。少了检查点，跑歪了只能从头再来；少了权限边界，你不敢让它碰生产环境。

最后是成本。**没有迭代上限的 goal 循环，无人看管时能烧掉惊人的额度**——它不会因为方向错了就自己停，它会一直「努力」。所以上限和预算一定要设死，这也是面试时值得主动提的一句，说明你真跑过。

在 Claude Code 里，`/loop` 和 `/goal` 就是这套东西的入口。
