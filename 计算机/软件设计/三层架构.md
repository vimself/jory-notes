> 三层架构按「离数据库多远」把代码摞成三层：表现层收发 HTTP，业务逻辑层写规则，数据访问层只管增删改查。真正的收益是业务逻辑不再被焊死在 Servlet 里——定时任务、导入脚本、单元测试都能直接调它。

## 典型场景

写一个注册功能。规则很朴素：用户名不能重复，所以要先查一次，没查到才插入。

这两步你顺手写进了 `UserRegisterServlet.doPost`。两周后陆续来了三件事：

- 管理后台也要能建用户，那是另一个 Servlet
- 运营发来一个 Excel，要写命令行脚本批量导入
- 测试想验证「重名必须失败」这条规则

三件事需要的都是同一段「查重 + 插入」，可它现在长在 `doPost` 里，入口参数是 `HttpServletRequest`。脚本里没有 request 对象，测试里也没有——想复用就得先伪造一个请求，谁都不愿意干这事，于是最省事的做法变成复制粘贴。等第三份拷贝出现，查重规则就开始各改各的了。

三层架构做的事就一件：**给这段逻辑找一个不认识 HTTP 的家。**

## 三层各自负责什么

![[三层架构-分层职责.png]]

| 层 | 干什么 | 典型类名 | 包 |
| --- | --- | --- | --- |
| **表现层**（web / controller） | 接收请求、把参数封装成对象、调业务逻辑层、把结果响应回去 | `UserListServlet` | `com.example.web` |
| **业务逻辑层**（service） | 封装业务规则，把数据访问层的基本操作组合成一个完整的业务动作 | `UserService` | `com.example.service` |
| **数据访问层**（dao / mapper） | 只对数据库做增删改查，一个方法对应一条 SQL | `UserMapper` | `com.example.mapper` |

「数据访问层」还有个更常见的叫法是 **DAO**（Data Access Object，数据访问对象）。用 [[MyBatis]] 的项目里它通常叫 mapper，因为这一层已经退化成了一个接口加一份 XML，连实现类都不用写。

调用方向是**单向**的：表现层调业务逻辑层，业务逻辑层调数据访问层，反过来一律不许。所以 `UserService` 里不该出现 `import jakarta.servlet.*`，`UserMapper` 里更不该出现。这条约束就是前面那个场景的解药——Service 不认识 HTTP，命令行脚本才能 `new UserService().register(user)`。

## 为什么不能少了 Service 层

初学时最容易冒出来的念头是：Service 里就一句 `return mapper.selectAll()`，中间加这一层不是脱裤子放屁吗？

这个质疑对了一半。**查询确实常常只是转发一下**。但写操作不是，理由有三个：

**一、事务边界在这一层。** 「查重 + 插入」是两步数据库操作，必须同生共死：查重通过了、插入却失败，不能留下半条数据。在 MyBatis 里，事务的单位是 `SqlSession`——一次 `openSession()` 到 `commit()` 之间的所有操作是一个整体。这个 `SqlSession` 该谁开、谁提交？只能是 Service。如果让 Dao 层每个方法各开各的 session，两步操作就落在两个事务里，你连回滚的机会都没有。

**二、一个业务动作往往要动好几张表。** 「下单」= 减库存 + 写订单 + 扣优惠券，对应三个 Mapper 的三个方法。谁把它们串成一个动作？Service。表现层不该知道下单要动三张表，就像点菜的人不用知道后厨有几个灶。

**三、它是复用的落点。** 回到开头那三个入口，它们共用的是 `userService.register(user)` 这一个方法调用，各自只负责把参数凑齐。

反过来说，如果你的项目就是个纯 CRUD 演示，每个 Service 方法都只有一行转发，那就大方地省掉它——**为了对称去造一堆空壳类，比少一层更糟**。分层是为了应对变化，不是为了摆造型。

## 和 MVC 的对应关系

![[三层架构-与 MVC 的对应关系.png]]

[[MVC 模式]] 和三层架构经常被摆在一起讲，然后被当成一回事。它们其实是两把方向不同的刀：

- **MVC 切的是角色**：一次请求里，谁接、谁算、谁显示
- **三层切的是层次**：代码按「离数据库多远」摞起来，上层只能调下层

叠在一起看，对应关系是这样的：

| MVC 里的 | 落在三层架构的哪 |
| --- | --- |
| Controller（Servlet） | 表现层 |
| View（JSP） | 表现层 |
| Model | 业务逻辑层 + 数据访问层 |

**关键在最后一行：MVC 的 Model 是个笼统的说法**，它同时包含了「业务规则」和「数据存取」两件事。三层架构把这个大块头劈成了两半——规则归 Service，存取归 Mapper。所以两者不是替代关系：你可以说「这个项目用了 MVC」，也可以说「这个项目分了三层」，说的是同一堆代码的两个侧面。

至于 View 和 Controller 为什么都算表现层：它们俩干的是同一件事的两头——一个把 HTTP 请求翻译进来，一个把结果翻译成 HTML 出去。换个前端（比如改成返回 [[JSON]] 给 [[AJAX]] 调），要动的只有这一层。

## 手把手：给整合案例补出 Service 层

[[Servlet 整合 MyBatis]] 里那个例子只有两层——Servlet 直接 `getMapper` 调 SQL。现在把中间那层补上，顺便实现开头说的注册查重。

**第一步，目录里多一个包。**

```text
src/main/java/com/example/
├── pojo/User.java
├── mapper/UserMapper.java          ← 数据访问层
├── service/UserService.java        ← 业务逻辑层（新增）
├── util/MyBatisUtil.java
└── web/UserListServlet.java        ← 表现层
```

**第二步，数据访问层加一个查询方法。** 接口里加一行，映射文件里加一段，一一对应：

```java
public interface UserMapper {
    List<User> selectAll();
    int insert(User user);
    User selectByUserName(String userName);      // 新增
}
```

```xml
<select id="selectByUserName" resultType="com.example.pojo.User">
  select id, user_name, age from tb_user where user_name = #{userName}
</select>
```

注意这个方法**只查数据、不做判断**。「查到了算重复」是业务规则，它属于上一层。

**第三步，业务逻辑层。** 这个类里没有一个 HTTP 相关的词：

```java
package com.example.service;

import com.example.mapper.UserMapper;
import com.example.pojo.User;
import com.example.util.MyBatisUtil;
import org.apache.ibatis.session.SqlSession;

import java.util.List;

public class UserService {

    public List<User> findAll() {
        try (SqlSession session = MyBatisUtil.openSession()) {
            return session.getMapper(UserMapper.class).selectAll();
        }
    }

    /** 注册成功返回 true；用户名已被占用返回 false，一行数据都不会写进去 */
    public boolean register(User user) {
        try (SqlSession session = MyBatisUtil.openSession()) {
            UserMapper mapper = session.getMapper(UserMapper.class);

            if (mapper.selectByUserName(user.getUserName()) != null) {
                return false;                    // 没 commit，什么都没发生
            }

            mapper.insert(user);
            session.commit();                    // 两步都走完了才提交
            return true;
        }
    }
}
```

`register` 里那一个 `SqlSession` 罩住了查和写两步，这就是「事务边界在 Service」的字面意思。`MyBatisUtil.openSession()` 默认不自动提交，漏掉 `commit()` 的表现是日志里 SQL 执行了、数据库里查不到——这个坑 [[Servlet 整合 MyBatis]] 里踩过一次。

**第四步，表现层瘦下来。**

```java
@WebServlet("/user/list")
public class UserListServlet extends HttpServlet {

    private final UserService userService = new UserService();

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {

        req.setAttribute("users", userService.findAll());
        req.getRequestDispatcher("/WEB-INF/views/list.jsp").forward(req, resp);
    }
}
```

改造后最值得看的是 **import 列表**：`SqlSession`、`UserMapper` 全没了，Servlet 只认识 `UserService` 和 `User`。反过来，`UserService` 的 import 里也没有任何 `jakarta.servlet` 的东西。两边各说各的语言，中间靠 `User` 对象接头——这就是分层完成的标志。

注册的 Servlet 同理，`doPost` 里只剩下「凑参数、调 service、按返回值决定跳哪」：

```java
User user = new User();
user.setUserName(req.getParameter("userName"));
user.setAge(Integer.valueOf(req.getParameter("age")));

if (userService.register(user)) {
    resp.sendRedirect(req.getContextPath() + "/user/list");
} else {
    req.setAttribute("msg", "用户名已被占用");
    req.getRequestDispatcher("/WEB-INF/views/register.jsp").forward(req, resp);
}
```

## 分层的三条纪律

**一、依赖只能向下。** `web → service → mapper`。Service 里出现 `HttpServletRequest`、Mapper 里出现 `HttpSession`，都说明这一层被污染了，前面所有好处当场归零。

**二、每层说自己的语言。** 表现层拿到的是一堆 `String` 参数，它有责任转成 `User` 对象再往下递。把 `request` 整个透传给 Service 是最常见的偷懒，代价是白分了一层——Service 照样只能在 Web 环境里跑。

**三、别把「一个方法一行」当成失败。** 转发型的 Service 方法是正常的，它占住了一个位置，等着将来加缓存、加权限校验、加事务。真正的失败是相反的情况：Servlet 里出现 SQL，或者 JSP 里出现业务判断。

至于「Service 要不要写成接口 + `UserServiceImpl` 实现类」，看情况：需要按环境替换实现、或者框架要求接口时才有必要；只有一个实现的时候，直接写类完全没问题。
