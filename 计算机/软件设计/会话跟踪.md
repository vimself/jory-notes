> HTTP 每处理完一个请求就把你忘了，所以「我是谁」得靠请求自己带。Cookie 把凭证存在浏览器、每次请求自动捎回来；Session 把数据存在服务器、只让浏览器捎一个编号。两者不是二选一——Session 认人靠的正是一个叫 `JSESSIONID` 的 Cookie。

## 典型场景

登录页填对了用户名密码，跳转到首页，首页上要显示「你好，张三」。

问题出在跳转之后。首页是**另一个请求**，服务器处理它的时候，手里只有一行 `GET /index.jsp` 和一堆请求头，没有任何东西写着「这是刚才登录成功的那个人」。你在登录那个方法里查出来的 `User` 对象，方法一返回就被回收了。

再点进「我的订单」，又是一个新请求，同样的失忆。

会话跟踪要解决的就是：**让服务器在一连串请求之间认出「这些是同一个人发的」。**

## HTTP 为什么记不住你

[[HTTP]] 是无状态协议：服务器处理完一个请求就把这次交互忘干净，下一个请求过来时它不记得你是谁。这不是设计缺陷，是刻意为之——服务器不用为每个来访者维护状态，扩容才简单。

代价就是「登录状态」这类东西得自己打补丁，而补丁只有两个方向：

| 思路 | 数据存哪 | 代表 |
| --- | --- | --- |
| 每次请求都把身份信息**带在身上** | 客户端（浏览器） | Cookie |
| 服务器把信息**存起来**，客户端只带一个编号 | 服务端（内存或别的存储） | Session |

下面两节分别讲这两条路，最后一节讲怎么选。

## Cookie：凭证存在浏览器

### 在报文里长什么样

Cookie 全靠一对请求头和响应头工作。服务器想让浏览器记住什么，就在响应里发一个 `Set-Cookie`：

```text
HTTP/1.1 200 OK
Set-Cookie: username=zhangsan; Max-Age=604800; Path=/app
Content-Type: text/html;charset=utf-8
```

浏览器收到后把它存起来。此后**只要访问的地址落在 `Path` 范围内**，它会自动在请求里带上：

```text
GET /app/index.html HTTP/1.1
Host: localhost:8080
Cookie: username=zhangsan
```

两个细节值得留意：**发的时候是 `Set-Cookie`、带回来的时候是 `Cookie`**，名字不一样；带回来的那行只有键值对，`Max-Age`、`Path` 这些属性是给浏览器看的指令，不会回传。

「自动带上」是浏览器的行为，不需要 JavaScript 参与，也不需要你在表单里藏隐藏域。这既是 Cookie 好用的地方，也是它后来惹出 CSRF 这类麻烦的根源。

### Servlet 里怎么读写

发一个 Cookie 两行：

```java
Cookie cookie = new Cookie("username", "zhangsan");
cookie.setMaxAge(7 * 24 * 60 * 60);          // 存七天
cookie.setPath(req.getContextPath());        // 只在本应用下带回来
resp.addCookie(cookie);                      // 底层就是加一个 Set-Cookie 响应头
```

读的时候要绕一下——API 给的是数组，没有按名字取的方法：

```java
Cookie[] cookies = req.getCookies();
String username = null;
if (cookies != null) {                        // 这行判空不能省
    for (Cookie c : cookies) {
        if ("username".equals(c.getName())) {
            username = c.getValue();
            break;
        }
    }
}
```

**`getCookies()` 在没有任何 Cookie 时返回的是 `null`，不是空数组**，这是 API 白纸黑字写着的行为。直接 `for` 上去，第一次用无痕窗口访问就是一个 `NullPointerException`。

### 活多久：`setMaxAge` 的三种取值

| 传的值 | 含义 |
| --- | --- |
| **正数** | 存活这么多秒，写进浏览器的磁盘，关掉浏览器再打开还在 |
| **0** | 立即删除这个 Cookie |
| **负数** | 不持久化，浏览器一关就没了（**默认值是 -1**） |

「退出登录时清掉某个 Cookie」的标准写法就是第二行：**同名、同 path 建一个新 Cookie，`setMaxAge(0)`，再 `addCookie`。** 没有 `deleteCookie` 方法，删除就是用一个立即过期的同名 Cookie 覆盖它。

顺带一提，`Max-Age` 和老式的 `Expires` 属性同时出现时，按 RFC 6265 的规定 **`Max-Age` 优先**。

### 作用范围：path 和 domain

`setPath("/app")` 的意思是：只有访问 `/app` 及其子路径时才带上这个 Cookie。默认值是当前请求所在的目录，这个默认往往不是你想要的——在 `/app/user/login` 里发的 Cookie，默认只在 `/app/user/` 下面回传，首页 `/app/index.jsp` 收不到。**所以 `setPath(req.getContextPath())` 几乎是标配**，意思是「整个应用范围内都带上」。

`setDomain` 控制域名范围，默认只回给发它的那台服务器。跨子域共享（`a.example.com` 和 `b.example.com` 用同一个 Cookie）才需要动它。

### 三个坑

**一、值里不能有空格、逗号、分号、等号这些字符。** Cookie 的值有字符限制，中文更是直接不行。要存就先编码：

```java
String value = URLEncoder.encode("张三", StandardCharsets.UTF_8);
// 读出来时
String name = URLDecoder.decode(value, StandardCharsets.UTF_8);
```

**二、它很小，而且是每个请求都要背着走的行李。** RFC 6265 只要求浏览器保证「每个 Cookie 至少 4096 字节（名字 + 值 + 属性加起来）」「每个域名至少 50 个」。超出部分怎么处理各家自己定。所以 Cookie 存的应该是**编号或开关**，不是数据本身。

**三、它在用户手里。** 存在浏览器里的东西，用户能看、能改、能伪造。`Set-Cookie: role=admin` 这种写法等于把权限控制交给了客户端。真正的身份信息要么放服务端（下一节），要么带签名。

## Session：数据存在服务器

### 原理：服务器发一个编号

Session 的思路是把 Cookie 那条路走到极致：**浏览器只存一个谁也看不懂的编号，真正的数据留在服务器上。**

第一次调用 `req.getSession()` 时：

```text
① 容器在服务端创建一个 HttpSession 对象，分配一个唯一 id
② 响应里自动带上   Set-Cookie: JSESSIONID=8F3A...C1; Path=/app; HttpOnly
③ 浏览器存下这个 Cookie
   ↓ 下一个请求
④ 请求头里带回  Cookie: JSESSIONID=8F3A...C1
⑤ 容器按 id 找回第 ① 步那个对象，getSession() 返回的还是它
```

这个 Cookie 的名字是规范定死的：**会话跟踪 Cookie 的标准名字必须是 `JSESSIONID`**（容器可以通过自己的配置改名）。基于 Cookie 的会话跟踪是规范要求所有容器都必须支持的机制。

所以「Cookie 和 Session 二选一」是个误解——**Session 本身就架在 Cookie 上**。用户如果禁用了 Cookie，Session 也跟着失效。规范里还留了一条退路叫 URL 重写：把会话 id 编码成 URL 里的路径参数，形如 `http://www.example.com/catalog/index.html;jsessionid=1234`。规范自己也说这是「最低标准的做法」，会把会话 id 暴露在日志、书签、`Referer` 和地址栏里，凡是 Cookie 可用的场合都不该用它。

### 常用 API

```java
HttpSession session = req.getSession();      // 没有就创建一个
session.setAttribute("user", user);          // 往里存对象，键是 String
User u = (User) session.getAttribute("user");// 取出来要强转
session.removeAttribute("user");             // 删一个
session.invalidate();                        // 整个作废
```

`getSession()` 有两个版本，区别是最容易出岔子的地方：

| 写法 | 没有现成会话时 |
| --- | --- |
| `getSession()` | **创建一个新的**，永远不返回 `null` |
| `getSession(false)` | 返回 `null` |

**判断「用户登没登录」必须用 `getSession(false)`。** 用无参版本的话，你每检查一次就给这个没登录的访客创建一个会话对象，爬虫扫一圈能给你创建出几万个空会话，全占着内存等超时。

还有一条约束：`getSession()` 必须在响应提交之前调用。原因回头看上面的流程——创建会话要发 `Set-Cookie` 响应头，而响应头一旦发出去就改不了了，这时候再要求容器建会话只能抛 `IllegalStateException`。

`setAttribute` 有个小陷阱：**值传 `null` 等价于调 `removeAttribute`**，不是存了一个空值进去。

### 超时：两个 API 的单位不一样

会话不会自己说「我走了」——HTTP 里没有「客户端离开」这个信号，唯一能用的判据是**多久没再发请求**。所以每个会话都有一个超时时间，从上一次请求算起。

改超时有三个入口，**单位不统一，这是实打实的坑**：

| 入口 | 单位 | 用法 |
| --- | --- | --- |
| `HttpSession.setMaxInactiveInterval(int)` | **秒** | 只影响当前这一个会话 |
| `ServletContext.setSessionTimeout(int)` | **分钟** | 整个应用的默认值 |
| `web.xml` 的 `<session-timeout>` | **分钟** | 同上，写在配置里 |

```xml
<session-config>
  <session-timeout>30</session-timeout>
</session-config>
```

Tomcat 自带的全局 `conf/web.xml` 里配的就是这个值，30 分钟。规范的说法是「默认超时时间由容器定义」，所以别的容器不一定是 30。

设成 **0 或负数表示永不过期**——除非你清楚自己在干什么，否则这等于内存泄漏。

### 关掉浏览器，会话并没有结束

这是初学时最容易记反的一条。关浏览器时消失的是 **`JSESSIONID` 那个 Cookie**（它默认不设 `Max-Age`，属于关掉就没的会话 Cookie），服务端那个 `HttpSession` 对象**还在**，一直待到超时才被回收。

所以：

- 用户以为自己「关掉浏览器就退出了」，其实只是丢了钥匙，房间还在
- 真正的退出登录必须显式调 `invalidate()`
- 服务器重启时会话通常就没了（除非容器做了持久化），表现是所有人都被踢下线

## 手把手：登录、首页、退出

假设 `User` 上多了个 `password` 字段，`UserService.login(userName, password)` 对得上就返回那个 `User`，对不上返回 `null`（业务逻辑为什么放在 Service 里，见 [[三层架构]]）。

**登录：把人存进会话。**

```java
@WebServlet("/user/login")
public class LoginServlet extends HttpServlet {

    private final UserService userService = new UserService();

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {

        req.setCharacterEncoding("UTF-8");
        User user = userService.login(req.getParameter("userName"),
                                      req.getParameter("password"));

        if (user == null) {
            resp.sendRedirect(req.getContextPath() + "/login.jsp?error=1");
            return;
        }

        req.changeSessionId();                       // 换一个新的会话 id
        req.getSession().setAttribute("user", user); // 认人靠这一句
        resp.sendRedirect(req.getContextPath() + "/index.jsp");
    }
}
```

`changeSessionId()` 那行是防**会话固定攻击**：攻击者先自己拿一个会话 id、想办法让受害者用这个 id 去登录，登录成功后他手里那个 id 就成了受害者的凭证。登录成功的瞬间换一个新 id，旧 id 立刻作废，这条路就断了。这个方法只换 id、不换对象，存在会话里的东西不会丢。

**首页：从会话里把人取回来。** JSP 里直接用 EL 读 session 域（域的概念见 [[JSP]]）：

```jsp
<h2>你好，${sessionScope.user.userName}</h2>
```

**退出：把会话作废。**

```java
@WebServlet("/user/logout")
public class LogoutServlet extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {

        HttpSession session = req.getSession(false);
        if (session != null) {
            session.invalidate();          // 对象作废，里面的属性全部解绑
        }
        resp.sendRedirect(req.getContextPath() + "/login.jsp");
    }
}
```

这里同样用 `getSession(false)`：都要退出了，没有会话就什么都不用做，没理由再新建一个。

至于「每个页面都要检查有没有登录」这件事，别在每个 Servlet 开头复制一遍判断——那是 [[Servlet 过滤器]] 的活。

## Cookie 还是 Session

| | Cookie | Session |
| --- | --- | --- |
| 数据存在 | 浏览器 | 服务器 |
| 能存多大 | 每个约 4 KB，且每次请求都要传 | 受服务器内存限制，不占带宽 |
| 能存什么 | 只能存字符串 | 任意 Java 对象 |
| 安全性 | 用户可见可改 | 用户只拿到一个 id |
| 默认活多久 | 关浏览器就没（可设 `Max-Age` 延长） | 一段时间不活动就超时（Tomcat 默认 30 分钟） |
| 关掉浏览器后 | 设了 `Max-Age` 就还在 | 对象还在，但钥匙丢了 |

选择原则两句话：**敏感的、大的、结构化的东西放 Session；不敏感、要长期留着、丢了也无所谓的放 Cookie。** 登录状态、购物车放 Session；「记住我的用户名」「上次选的主题色」放 Cookie。

有一个前提值得先说清楚：Session 的数据在**某一台**服务器的内存里。应用扩到多台机器时，用户下一个请求被负载均衡打到另一台，那台上没有他的会话——这时要么让负载均衡把同一个人固定送到同一台，要么把会话搬到 Redis 这类共享存储里。单机开发时感受不到，上线前必须想到。
